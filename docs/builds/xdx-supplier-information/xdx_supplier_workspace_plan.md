# XDX Supplier Workspace — proposed plan

Planning draft for review. No app implementation or live operations are authorized by this document. Confirmed email scope: **summary in the message only; no attachment**. PDF is a separate download.

## Objective and recommended design

An Oracle Fusion AI Agent Studio web app for signed-in procurement/supplier-management users to query suppliers and child records, create suppliers and/or children, show complete persisted data, download a PDF and send a reviewed summary email.

| Approach | Trade-off | Recommendation |
| --- | --- | --- |
| Agent Studio app using existing BO and native templates/communications | Reuses Fusion integration; PDF/download and actual email delivery still need proof | Start here |
| Same app plus an approved export/mail integration | Fills a proven native gap but adds authentication/deployment/support work | Add only if capability discovery proves necessary |
| Separate custom web app | More UI control but duplicates hosting/authentication/integration | Not preferred for this project |

Proposed name/code: **XDX Supplier Workspace / XDX_SUPPLIER_WORKSPACE**. Reuse the existing XDX_SUPPLIER_INFORMATION BO. Use a focused app-backed workflow with explicit routes; deterministic code owns input validation, pagination, write sequencing and persisted-value comparison. Models interpret intent and draft grounded summaries. Avoid extra specialist workflows without a distinct reusable responsibility.

Initial children: **addresses, sites and contacts**. Support a new supplier alone, a new supplier with selected children, or new children for an existing supplier. Updates/deletes, bulk import, bank accounts, site assignments and contact-user provisioning are outside initial scope. Existing POST templates cover a bounded field set, not all writable Fusion fields; freeze the required create-field contract before implementation and extend deliberately where needed.

## User journey

1. **Start:** search and Create Supplier actions, with a selected-record/task area. No catalog preload or required launch context. Validate any optional launch supplier ID.
2. **Find:** query by name, number or ID where supported. Show multiple matches for explicit selection. Child-only queries resolve a supplier first. Allow only validated child filters; raw prose never becomes a REST expression. Global cross-supplier child search needs separate scope.
3. **Inspect:** profile, addresses, sites and contacts in separate sections; users choose selected child types or all details. Display counts, nulls, empty results and retrieval status.
4. **Create:** guided editable forms, collecting missing business inputs and resolving valid references through supported lookups. Preview the exact supplier, payloads and operation set. One explicit confirmation covers that set; changed scope needs renewed confirmation.
5. **Confirm:** read back persisted parent/children, compare intended fields, and display generated IDs, server defaults and per-operation outcomes. Never claim success from HTTP status alone.
6. **Download PDF:** full selected supplier dossier, readable across pages, from the verified displayed data version.
7. **Email summary:** editable recipients, subject and concise grounded body; explicit Send confirmation. No attachment and no automatic selection of supplier-contact recipients.

## Complete-data and write contracts

Complete means all authorized scalar supplier fields and all authorized fields/records across **every page of each selected child collection**. All details selects the profile plus all three child types. Preserve nulls as Not provided, show zero counts, and label omitted/restricted sections. UI paging may limit rows on screen, not the underlying selected data. Service errors, limits or missing pages must produce an explicit incomplete state, never a complete claim.

One canonical structured dossier owns supplier identity, records, selected scope, counts, capture timestamps and completeness/errors. Display, PDF and email consume the same version. Keep large datasets out of repeated model prompts. Multiple REST reads are not an atomic snapshot; label capture times and do not silently combine refreshed data with a reviewed export/email.

Resolve a stable SupplierId and use it in every child path. Paginate each resource independently with stable ordering; detect duplicates and non-advancing pages. Validate types, filters and escaping. No arbitrary first-match supplier selection.

Create in dependency order: parent if needed, address before its site, contact under the resolved parent. Omit confirmed autogenerated own IDs; retain valid parent/foreign references. Preserve SupplierType and every approved business field. Compare an independent intended-field inventory against request, POST response and verification GET, including omitted expected fields. Tool errors never justify silently dropping business requirements.

Persist per-operation receipts and IDs. On partial failure, show successful records and the failed step, retain the draft and reconcile before resuming unresolved work. Do not repeat successful POSTs or promise transaction rollback. Guard duplicate clicks; unknown write outcomes require GET reconciliation before retry. Client-side guards alone do not prove server idempotency.

## PDF and email

PDF: supplier header, full profile/selected child sections, counts, capture time and missing values. Use continued tables/appendices for large data. Validate a real PDF, render every page, compare records/fields with the dossier and prove download. Partial exports remain labeled incomplete.

Email: summary only—supplier name/number, type/relationship, child counts and key details or creation results, timestamp and incomplete scope if any. Review recipients and edited content, then send through an approved configured sender/channel. Record actual provider status; do not label acceptance as confirmed delivery. Handle repeat clicks and uncertain send outcomes without automatic duplicate sends.

Local guidance defines PDF/email templates and communications. This is configuration support, not proof of rendering/download or actual email delivery. Validate both early. The CLI's HCM email tool types do not alone establish procurement suitability. If an approved send channel is absent, identify the exact dependency; draft-only email does not meet the objective.

## Implementation sequence

| Slice | Deliverable | Acceptance evidence |
| --- | --- | --- |
| S0 | Approved intake, field contract, BO runtime path, PDF/download and email-send capability | Exact supported mechanisms and unresolved dependencies documented |
| S1 | Search, selection and complete dossier | Correct identity; ambiguity handling; empty/multi-page children; truthful error/incomplete state |
| S2 | New supplier, parent-with-children and existing-parent child creation | Reviewed payloads; generated IDs; independent field checks; correct parent/site-address relationships; partial/uncertain outcomes without duplicates |
| S3 | PDF download | Valid rendered PDF, complete field/row parity and working download |
| S4 | Summary email | Correct recipients/body, no attachment, cancel without send, confirmed send action and provider receipt |
| S5 | Integrated app journey | Search → inspect → create approved test records → GET/display → PDF download → approved summary email; actual UI and scoped test evidence |

Each test maps to an approved requirement slice, owner, route and terminal output. Run focused static/local checks before the authorized golden path; follow current ATLAS workflow/app synchronization afterward. Local BO tests do not prove deployed app behavior. This planning request authorizes no test supplier writes or real email sends.

## Build startup and approval boundary

After scope approval, start a fresh run and create branch `codex/xdx-supplier-workspace` and worktree `.worktrees/xdx-supplier-workspace` from committed governance. Initialize build records under `docs/builds/xdx-supplier-workspace/`, carry forward approved planning documents, inspect package layout and complete startup verification, session gate, requirement slices, architecture self-review and MVP manifest. Reuse existing BO/evidence; do not replace current governance with an older installed seed.

Keep timing/tokens/AI Units or unavailability reasons, scoped test/export/send evidence, object learnings and one active handoff. Deployment, publication, live writes/sends and Git push require established scope. The full objective is incomplete until query, create, complete persisted display, PDF download and real summary email all have evidence.

Review assumptions: Agent Studio target; procurement/supplier-management users; three child types; no required launch context; review before creates and sends. Email-summary-only is confirmed. Sender/channel, eligible reference lookups and native PDF runtime support are capability-discovery items, not promised implementations.
